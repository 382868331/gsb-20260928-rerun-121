# 多版本配置分发系统（configdist）

用 Go 实现的服务端 + 多个本地虚拟客户端，演示**整份配置的可靠切换**
（不是文件同步工具）。

## 核心语义

- 每个版本是一份**完整配置快照**（非增量）。客户端缺少中间版本时，
  直接拉取最新完整版本即可生效。
- 客户端切换是**原子**的：配置先写入暂存文件并校验，再 `rename` 覆盖
  当前生效配置；应用失败时原配置保持不变。
- 服务端严格区分两种确认：
  - `downloaded`：客户端仅完成下载，**不代表应用成功**；
  - `verified`：客户端完成校验和 + 业务校验，**仍不代表已生效**；
  - `applied`：客户端确认新配置已实际生效。
  是否可推广只看 `applied`，绝不因大多数客户端下载/校验成功就认定可推广。
- 每个客户端对每个版本的状态**单调推进**：
  `pending → downloaded → verified → applied`，或 `→ failed`。
  重复确认、乱序确认都不会把状态回退（例如已 `applied` 后再收到
  `downloaded` 或 `failed` 不会改变结果）。
- 应用失败会保留失败原因，且该客户端对更新版本仍处于 `pending`
  待处理状态，下次同步继续。
- **分批放量**：发布时可携带 `batches`（客户端分组），首批放行后，
  当前批全部 `applied` 才放行下一批；任一批出现 `failed` 即
  **自动停止后续批次**，失败客户端保留旧版本与失败原因。
- **明确回退**：`/admin/v1/rollback` 发布回退目标版本，所有客户端
  目标改为该版本（包括从新版本降级）；每个版本的失败历史独立保存，
  回退不覆盖原失败历史。
- 服务端只接受针对**当前目标版本**的确认：迟到的旧版本确认直接忽略，
  不会把回退中的客户端重新标成新版本已完成。
- 服务端把版本与客户端状态持久化到磁盘；服务端/客户端重启或短暂
  断连后，客户端心跳上报**实际生效版本**，服务端据此对账恢复。
  确认丢失（如 `applied` 未送达）也由心跳对账按实际版本补记。

## 快速开始

```bash
go run ./cmd/simulate
```

该演示会：启动服务端与 4 个本地虚拟客户端（正常 / 应用失败 /
确认丢失 / 离线）→ 发布 v1 → 分三批发布 v2，批次 2 应用失败后
自动停止批次 3 → 发布回退目标 v1（已升级的客户端降级回来，失败
历史保留）→ 重放迟到的 v2 确认（被忽略）→ 重启服务端按实际
生效版本对账。

也可以手动运行：

```bash
go run ./cmd/server  -addr 127.0.0.1:8080 -data ./runtime-data
go run ./cmd/client  -server http://127.0.0.1:8080 -id client-1 -data ./c1
curl -X POST localhost:8080/admin/v1/releases -d '{"content":{...}}'
```

## HTTP API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/admin/v1/releases` | 发布一份完整配置，版本号自增；可带 `batches` 分批放量 |
| POST | `/admin/v1/rollback` | 发布明确的回退目标版本，停止进行中的放量 |
| GET | `/admin/v1/status` | 查看放量进度、各客户端实际/目标版本、状态与版本历史 |
| GET | `/api/v1/releases/latest` | 获取最新完整快照 |
| GET | `/api/v1/releases/{version}` | 下载指定版本完整快照（可跳过中间版本） |
| POST | `/api/v1/register` | 注册/心跳：上报 `active_version` 对账，返回**目标版本**（可能低于最新版，如未到批次或回退中） |
| POST | `/api/v1/ack` | 确认：`downloaded` / `verified` / `applied` / `failed`（可带 `reason`） |

`downloaded` / `verified` / `applied` 是三个独立确认；服务端只有在
收到 `applied` 后才把客户端的实际版本前移。状态机单调推进，重复确认幂等。
